# 并发保存与自动保存：设计、理由与代价

这份文档回答两个没有现成答案的问题，并记录修复前的两个 bug 与复现方式。

承诺：**别处改过了，这边既不能悄悄覆盖对方，也不能悄悄丢掉自己。**

---

## 1. 服务端：谁来保证“核对基准修订”和“写入新修订”不可分割

### 结论

交给 **SQLite 的写事务（`BEGIN IMMEDIATE`）裁决**，不用进程内队列作为正确性手段。
进程内的 `threading.RLock` 只负责让同进程的多个线程不在同一个连接上交错
`BEGIN/COMMIT`，它不提供跨进程保证。

### 修复前为什么会 500

旧实现把一次保存拆在两个事务里：

1. 事务 A：`get_meta()` 读 `documents.current_revision`（比如读到 1，与
   `base_revision=1` 相符，检查通过）；
2. 事务 B：`INSERT revisions ... revision=2`，再 `UPDATE documents ...`。

两步之间会释放进程锁。两个同基准请求可以都在步骤 1 看到修订 1，然后都去插入
修订 2：

```
sqlite3.IntegrityError: UNIQUE constraint failed: revisions.document_id, revisions.revision
```

这个异常没有被翻译成 409，直接冒成 **500**。输的一方既没存上，也没拿到冲突
信息；客户端只能看到“服务器炸了”。这就是“十几个请求里有一部分 500、错开就
没事”的原因——错开时两步之间没有别的请求，竞态窗口碰不上。

### 修复后的步骤（`storage.save_revision`）

整条保存放在**一条**写事务里：

```sql
BEGIN IMMEDIATE;                       -- 立刻取得库级 RESERVED 写锁
SELECT current_revision FROM documents WHERE id = ?;
-- 与 base_revision 不符 → 在同一事务内读当前内容，ROLLBACK，返回 409
INSERT INTO revisions ...;             -- current+1
UPDATE documents SET current_revision = ? ...;
COMMIT;
```

- `BEGIN IMMEDIATE` 在**第一条语句**就拿到写锁，而不是等到 `INSERT` 才升级。
  抢不到锁的连接在 `busy_timeout`（当前 5s）内等待，不会立刻报
  `database is locked`。
- 持锁期间读到的 `current_revision` 一定是已提交的最新值；读、判、插、推进
  对其他进程表现为**一个原子时刻**。第二个拿到锁的请求看到的已经是赢家推进
  后的修订号，于是老老实实在事务内得到冲突并回滚——它从未插入过半行。
- 唯一键 `(document_id, revision)` 是**第二道防线**：哪怕将来有人改掉事务
  策略，撞号也只会抛 `IntegrityError`，代码把它兜底翻译成 409（重新读一次
  当前修订与内容），绝不会再冒成 500。

因此同基准并发保存，无论多少个，结果恒为：**恰好一个 200 写出新修订，其余
全部 409**，带回 `current_revision` 与 `current_content`；修订链连续、不跳不重。

### 为什么不用“进程内排队”

进程内串行化（一把锁包住 check+insert）在**单进程**里也能修好这个 bug，而且
更简单。但它回答不了“多个服务进程共用同一个库文件”：

- 两个 uvicorn/gunicorn 进程各有各的锁，互不可见，竞态原样存在；
- 正确性会依赖部署形态（“只能开一个进程”），这是最容易在扩容时被踩中的坑。

数据库本来就知道提交顺序，由它裁决最直接，且应用层无状态、可水平扩。

### 多进程还站得住吗：代价与边界

站得住，但有明确代价和边界：

1. **写串行**：SQLite（含 WAL）同一时刻只允许一个写事务。同一份讲稿的并发
   保存本来就必须串行裁决，这没有额外损失；但要知道**全库**的写也是串行的——
   不同讲稿之间的写同样排队。对写作台这种写少读多、单次写入极小的负载没有
   问题；若变成高并发写入服务，应换 PostgreSQL 之类的客户端-服务器数据库，
   并把同样的“行锁 + 事务内核对”搬过去（`SELECT ... FOR UPDATE` 或在
   `UPDATE ... WHERE current_revision=?` 上看行计数）。
2. **等待有界**：`busy_timeout=5000`。极端拥塞下超过 5 秒会收到“锁忙”错误，
   语义上应表现为可重试的 503，而不是数据损坏。当前单次写事务是毫秒级，这个
   余量足够。
3. **WAL 前提**：已开启 `journal_mode=WAL`，读写不互阻塞；所有进程必须访问
   同一个文件系统（WAL 的 `-shm/-wal` 旁路文件要求如此），网络盘上的 SQLite
   不在承诺范围内。
4. **连接归属**：每个 `Storage` 一个连接、`check_same_thread=False`，同进程
   线程的事务边界由进程锁串行。多进程时各自持有独立连接，由 SQLite 锁裁决。
5. **失败即回滚**：冲突路径在 `COMMIT` 之前抛错，上下文管理器 `ROLLBACK`，
   不会留下“插了修订行却没更新指针”或反过来的半截状态。

验证见 `backend/tests/test_concurrency.py`：同进程 20 线程 × 8 轮、HTTP 线程池
20 并发、以及 **10 个独立 OS 进程共用同一个库文件**（进程内锁在该用例里完全
使不上力），均为恰好 1 个成功、其余干净 409、修订链 1→2。

### 顺带修掉的 API 层隐患

- 连接改为 `isolation_level=None`，事务边界全部显式控制，避免 Python sqlite3
  的隐式 `BEGIN` 与 `BEGIN IMMEDIATE` 互相干扰。
- 打开 `foreign_keys=ON`（修订行外键真正生效）。

## 2. 前端：保存没回来又接着敲字，下一次保存依据哪个修订号

### 规则：单飞（in-flight 去重）+ 响应后对账

任意时刻**至多一个在飞保存**：

- 在飞期间继续敲字，**不另发请求、不排队、不取消**在飞的那个；只记住“在飞
  之后内容又变了”。
- 在飞保存**成功**返回新修订号 `R` 后：
  - 刚提交的那份全文标记为已保存，本地基线推进到 `R`；
  - **比较此刻编辑器全文与刚存好的那份全文**：
    - 相同 → 顶栏“已保存 #R”，没有第二次请求；
    - 不同（用户在等待期间又写了）→ 只把“后来敲的内容”当成新改动，以 **R**
      为基线再存一次。**已经存好的那份不会被原样提交第二遍**，不会多出一个
      内容相同的空修订。
- 在飞保存**失败**：
  - 409 → 挂冲突框（见下），暂停自动保存，等用户裁决；在飞标记清掉，本地
    文字原样保留；
  - 网络错误/5xx → 顶栏如实显示失败，1.5s 后按**同一份未保存文本、同一基线**
    重试，绝不伪装成已保存。

### “在飞期间有没有新改动”怎么判定

只看一件事：**响应回来那一刻，编辑器全文是否还等于在飞请求提交的全文。**

不能用“与上一次已保存文本不同”来判断——冲突后“保留我的”另存的内容本来就与
旧的已保存文本不同，但那不是用户新敲的字。用错信号会在冲突解决后误触发一次
幽灵保存（这条由前端测试“保留我的另存成功”抓到并防回归）。

### 409 时这段新敲的内容怎么办

冲突的是“整份全文对整份全文”，本地不做静默三方合并（Markdown 的语义合并没有
可靠的自动答案）。处理原则：**一个字都不丢，选择权交给人**：

1. 被拒保存的全文（含在飞期间敲的字）仍在编辑框里，顶栏显示“有未保存的
   改动”，绝不回退、绝不谎称已保存；
2. 弹框同时给出两个修订号：**你基于第几修订**（纯客户端事实，服务端不知道，
   收到 409 时在本地把被拒请求的 `base_revision` 补进响应体）与**服务器当前
   第几修订**（服务端返回）；
3. 三个出口：
   - **采用服务器的**：编辑器与基线切到服务器当前版本（放弃本地改动）；
   - **保留我的**：以服务器**当前**修订号为新基线，把我的全文另存为最新
     修订——不是拿旧基线硬推，所以对方版本留在历史链里，不被覆盖；
   - **手动合并**：左右对照，编辑合并结果后同样以服务器当前修订为基线保存。
4. 若点“保留我的/合并保存”的瞬间服务器又被别人推进，会再吃一次 409，弹框
   带着更新后的修订号回来，对话可以一直继续到无冲突为止。

### 修复前页面上的两个 bug

- **新建后再也不保存**：一个副作用在每次敲字（且徽标处于 saved）时都把
  “最后已保存文本”刷成当前内容，使自动保存的“内容变了才发请求”守卫恒为
  假——网络面板里没有任何 PUT，顶栏却永远“已保存”。现在“已保存文本”只在
  保存成功/新建/采用服务器版三个时刻显式更新；dirty 由“当前全文 ≠ 已保存
  全文”直接派生，徽标显示 保存中 / 已保存 / 有未保存的改动，无法三者不一致。
- **冲突框的“第 ？ 修订”**：被拒基线号从未传给弹框，文案里写死了问号。
  现在由 409 处理处填入 `base_revision`。

### 代价与边界

- 去抖 800ms：停顿后约 0.8s 才发保存；最坏情况下未保存窗口就是这 0.8s 加上
  一次往返。可按需调小，不值得为此引入逐按键保存（会制造大量修订）。
- 最后一次去抖窗口内若进程崩溃/关页，那一小段还没落盘；生产环境可加
  `beforeunload` 提示或 `navigator.sendBeacon` 兜底（当前未做，属已知边界）。
- 单飞意味着极快的连续改动会聚合成“每往返最多一个修订”，对修订历史的可读性
  反而更好；代价是某个中间全文可能不对应任何一个修订号（本来也不该对应）。
- 前端不自动三方合并：取舍是宁可多问一次，也不悄悄拼出一份作者没见过的文本。

## 验证了什么

- `backend/tests/test_concurrency.py`（新增）：
  - 同进程 20 线程屏障并发、×8 轮：恰好 1 成功、其余 `ConflictError`，修订
    `[1,2]`；两批连号并发后修订 `[1,2,3]` 连续不跳不重；
  - HTTP（FastAPI 线程池）20 并发：恰好 1 个 200、19 个 409、无 5xx，每个
    409 都带 `current_revision/current_content/document_id`；
  - 10 个独立进程共用同一库文件：恰好 1 成功、其余 409（验证裁决来自数据库
    而非进程锁）。
- 既有 87 个后端测试全部保持绿色（解析、切页、增量对拍、容错、按修订取历史
  等行为未改）。
- `frontend/src/test/App.test.tsx`（新增，vitest + Testing Library + 假定时器
  + fetch 桩），共 7 个用例，验证的是页面状态机而非后端：
  新建后敲字停顿必定发出保存且徽标如实切换；无改动不发多余 PUT；连续敲字去抖
  成一次；在飞期间继续敲字只补存一次且基线推进、已存内容不重复提交；500 自动
  重试；409 弹框修订号正确、本地文字不丢，以及“保留我的 / 采用服务器 / 手动
  合并”三条路径各自携带正确的基线与正文。
