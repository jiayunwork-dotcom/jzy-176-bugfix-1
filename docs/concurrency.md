# 并发保存：原子性、乐观锁与前端在途编辑

这份文档回答“保存为什么靠不住、现在靠什么保证”，并讲清两个曾经
没有现成答案的设计抉择及其代价。承诺只有一句：

> 别处改过了，这边既不能悄悄覆盖对方，也不能悄悄丢掉自己。

---

## 1. 旧实现的两个 bug，都是同一个根因

### 1.1 接口侧：同基准并发保存出现 500

旧的 `Storage.save_revision` 把乐观锁拆成了两步：

1. **锁（事务）之外**读 `documents.current_revision`，和 `base_revision` 比；
2. 比对通过后，**另开一个事务**插入 `revisions(new_rev)`、更新 `current`。

单连接 + 一把进程 `RLock` 时，写事务本身串行，很多时序下侥幸不出错；
但 FastAPI 的同步路由跑在线程池里，只要“核对”和“写入”之间被调度
切开，两个请求就会**都**读到旧的 `current`、**都**判定通过、**都**
去插同一个修订号：

```
请求A: 读 current=1, base=1 通过 ──┐
请求B: 读 current=1, base=1 通过 ──┤（都在写之前）
请求A: INSERT revision=2  ────────┴→ 成功
请求B: INSERT revision=2 ─────────→ UNIQUE constraint failed → 500
```

线上“发十几个、一部分 500、错开就干净”正是这个窗口被调度命中的
概率现象。结果是：本该返回 409 的失败者拿到 500，前端无法把它
解释成冲突，作者既不知道自己没存上，也看不到冲突框。

### 1.2 页面侧：新建后再也不保存、双标签页静默丢稿

旧前端的自动保存 `useEffect` 依赖 `[content, docId, baseRevision, save]`，
而“是否真有改动”靠另一个 effect 在 `saveState` 变成 `saved` 时
把 `content` 抄进 `lastSavedRef`。这条链有两处致命断裂：

- **新建后不再触发**：`createNew` 把 `content` 存为 rev 1，但没有
  可靠地建立“服务端版本 = 当前文本”的基线；随后敲字时
  `content !== lastSavedRef` 的判定与保存 effect 的依赖时序错乱，
  定时器不发任何请求，顶栏永远停在“已保存”。
- **双标签页静默覆盖**：就算请求发出去，前端也没有把 409 稳定地
  接到冲突框；冲突框里“你基于第几修订”写死成问号。甲标签页基于
  旧 rev 继续写，服务端已是乙的新 rev，甲的内容在“已保存”的假象
  里丢失。

## 2. 抉择一：核对与写入靠什么不可分割？

**结论：交给数据库裁决，用一个 `BEGIN IMMEDIATE` 写事务把
“重读当前修订 → 决定写或拒 → 插入新修订 → 推进 current”全包住。
不采用“只在进程里排队”。**

### 2.1 现在的实现（`storage.py`）

```python
with self._write_tx():          # BEGIN IMMEDIATE，立刻拿 RESERVED/写锁
    row = SELECT current_revision FROM documents WHERE id=?
    if base_revision != row.current_revision:
        raise ConflictError(当前修订, 当前内容, 文档id, base_revision)
    INSERT INTO revisions(... new_rev ...)
    UPDATE documents SET current_revision=new_rev ...
# COMMIT
```

关键点：

- **`BEGIN IMMEDIATE` 而不是默认的 `BEGIN`（DEFERRED）**。DEFERRED
  事务在第一条读语句只拿共享锁、到第一条写才尝试升级成写锁；
  IMMEDIATE 在事务开始就取得写锁。于是“拿到锁 → 在锁内读 current →
  写 → 提交”对所有其它连接是一个不可分割的裁决区间：后来者要么在
  拿锁处排队，等先来者提交后读到的已是新 `current`，直接 409；
  绝不会出现两个事务都核对通过、抢插同号修订。
- 插入与更新在**同一事务**里提交，要么都生效要么都回滚，**没有
  写了一半的修订**。
- `revisions` 上的 `PRIMARY KEY(document_id, revision)` 是最后一道
  防线：即使将来有人改坏了事务边界，数据库也会拒绝重复修订号，
  而不是静默产生两条同号记录（配合把该错误视为冲突/失败，不外泄 500）。
- 修订号由“锁内读到的 current + 1”得到，写事务全局串行，所以
  **修订号连续、不跳不重**（1,2,3,…）。

配套设置：`PRAGMA journal_mode=WAL`（读写不互斥、崩溃可恢复）与
`PRAGMA busy_timeout=5000`（写锁正被占用时等待而不是立刻抛
`SQLITE_BUSY`）。连接用 `isolation_level=None` 由代码显式控制事务，
避免 Python sqlite3 在 DML 时隐式开 DEFERRED 事务。

### 2.2 为什么不用“只在进程里排队”

进程内一把锁（如 asyncio 队列 / 线程锁串行化所有 save）在**单进程**
里也能做到不重号，但它有两个无法接受的代价：

1. **多进程共用同一个库文件时完全失效**。锁是进程内的内存对象，
   第二个进程根本不知道它的存在；两个进程各自的“核对+写入”依旧
   交错。仓库里 `test_concurrency_multiproc.py` 起多个 OS 进程、
   各自持独立连接打同一个库文件，证明这种部署下仍然恰一个赢、
   其余 409——这只有数据库裁决才能做到。
2. 把正确性寄托在“应用层恰好串行”上，任何一条旁路（管理脚本、
   数据迁移、未来的第二个 worker）都会悄悄破坏不变量。

### 2.3 多进程共用一个库文件，这办法还站得住吗

**站得住**，因为裁决者是 SQLite 文件级的锁，而不是进程内存。
WAL 模式下同一时刻仍只允许一个写事务：多个连接/进程的
`BEGIN IMMEDIATE` 由 SQLite 排队，先拿到写锁者完成“读-判-写-提交”，
其余在 `busy_timeout` 内等待，拿到锁后重读 `current` 必然看到
已前进的修订号而得到 409。已用多进程测试对拍验证。

**代价与边界（需要知道）：**

- 写事务被**全库单写者**串行化。对“讲稿写作台”这种低频、小载荷
  （单文档 ≤ 2 MiB）写入完全够用；若未来变成高并发批量写入，
  吞吐会受单写者限制，届时应换用支持行锁/更强并发的数据库
  （PostgreSQL 等），但乐观锁的 SQL 形态（事务内条件更新）可直接迁移。
- `busy_timeout` 内仍拿不到锁会报 busy——这是明确的失败，而不是
  静默覆盖；调用方应把它当作可重试的临时错误（前端对非 409 错误
  会自动重试）。
- 这条保证针对的是“多个进程连**同一个库文件**”。若是多副本各自
  连**不同的**库（没有共享存储），任何数据库方案都无能为力，那是
  部署层面的数据归属问题，不在本机制承诺范围内。
- 网络文件系统（部分 NFS 等）上的 SQLite 锁语义不可靠；官方建议
  WAL 文件放在本地盘/可靠块存储卷上（docker-compose 用命名卷即此）。

### 2.4 409 响应携带的信息

```json
{ "error": "revision_conflict",
  "base_revision": 1,
  "current_revision": 2,
  "current_content": "……",
  "document_id": 1 }
```

`base_revision` 是**这次被拒保存所依据的修订号**（“你基于第几修订
在编辑”），`current_revision`/`current_content` 是服务端当前版本。
前端据此把冲突框的问号补成真实数字。

## 3. 抉择二：一次保存还没返回、人又接着敲字，下一次保存依据哪个修订号？

**结论：同一时刻只允许一个保存请求在飞（单飞）；在途期间的新敲内容
不另发请求，等在途保存返回后，以“刚确认保存成功的那个新修订号”为
基准，把最新全文再存一次。冲突时锁定自动保存、本地原文原样保留，
交冲突框处理。**

### 3.1 修订号依据

前端维护 `baseRevRef`：本页下一次保存应带的基准修订号。

- 保存**成功**：前移到响应里的新修订号（这是服务端承认的最新版本）。
- 在途保存期间继续敲的字，语义上是“在刚存好的那一版**之上**的新
  改动”，所以后续保存用**新**修订号，绝不会再用旧号（用旧号必然
  409，甚至在旧的坏后端下覆盖别人）。
- 保存**冲突**：基准不动，弹出冲突框由人决定，不自动重试。
- 保存遇到**网络/5xx**：基准也不动，稍后用同一基准重试同一内容。

### 3.2 单飞 + 合并，避免并发自撞

若在途时为每个防抖都发一个 PUT，同一标签页会自己和自己产生竞态
（两个请求带同一基准，后一个吃 409）。因此：

```
敲字 → 停 800ms → 发 PUT(content=T1, base=B)   // saveRunning=true
        在途期间又敲字 → 只更新 contentRef，不发第二个
PUT 返回 rev=B+1：
   lastSaved = {T1, B+1}; baseRev = B+1
   若 contentRef(=T2) ≠ T1 → 标脏并再安排一次 PUT(T2, base=B+1)
   否则 → 已保存(B+1)
```

- 任一时刻最多一个在飞 PUT，不会自己撞自己。
- 在途期间的新敲内容**不丢**：返回后发现 `contentRef` 比刚存的新，
  自动再存一次。
- **不把已存内容当新改动重发**：保存前比对
  `contentRef` 与 `lastSaved.text`（同时确认基准一致），相等就不发
  请求——没有净改动不产生新修订。`lastSaved` 只在“保存成功 /
  新建 / 采用服务端版本”时更新，是“有没有未保存改动”的唯一判据。

### 3.3 顶栏状态如实反映

状态机：`保存中(saving)` / `已保存(saved, rev)` /
`有未保存的改动(dirty)` / `冲突(conflict)` / `失败将重试(error)`。

- 敲字后停一小会儿一定进入“保存中”，成功后“已保存（修订 #n）”，
  在途期间又改则短暂显示“有未保存的改动”并续存。
- 不再有“实际没发请求却显示已保存”的状态：`saved` 只在真正收到
  成功响应后置位。

### 3.4 冲突时新敲内容怎么处置

收到 409：

1. 置 `conflictRef`，**锁定编辑器与自动保存**（防止在人做决定期间
   又有自动 PUT 把水搅浑）；本地全文原样保留，绝不丢弃。
2. 冲突框写明“你基于第 `base_revision` 修订 / 服务器当前第
   `current_revision` 修订”，并展示服务端内容。
3. 三个出口，结果各自正确：
   - **采用服务器版本**：内容与基准换成 `current_content/current_revision`，
     不另发请求；本地未保存改动按选择放弃。
   - **保留我的**：把本地全文以 `current_revision` 为基准另存为最新
     修订（一次合法的“接力”保存），成功后基准前移；服务端上一版
     （对方的修订）仍在不可变历史里，没有被覆盖。
   - **手动合并后保存**：左右对照，编辑合并结果，同样以
     `current_revision` 为基准保存。
4. 做决定的瞬间若又有第三端写入（极罕见），这次保存会再吃 409，
   弹回冲突框，本地文本依旧不丢。

## 4. 验证了什么

### 4.1 后端（pytest）

- `tests/test_concurrency.py`：多个**各自独立连接**的线程共用同一
  库文件，16 路同基准并发、连跑 5 轮，用“事务外核对后在写事务门口
  汇齐、统一放行”的门稳定制造最大竞态。断言：恰 1 个成功、其余
  全 `ConflictError`、无任何其它异常（旧 bug 的 IntegrityError）、
  修订链 1..N 连续不跳不重、服务端停在唯一胜者版本、每个 409 带回
  正确的 current/base/content。
- `tests/test_api.py`：HTTP 层 16 路并发 PUT，恰一个 200、其余 409、
  绝无 500，响应体字段齐全；另有不设门的 12 路 ×10 轮原始时序对拍。
- `tests/test_concurrency_multiproc.py`：多个 **OS 进程**、独立连接、
  同一库文件，验证多进程部署下结论不变。
- **红绿对照**：把 `save_revision` 临时还原成旧的“锁外核对 + 独立
  写事务”，上述并发测试全部失败（IntegrityError/500）；恢复新实现
  后全部通过。既有 87 个解析/容错/增量/存储/HTTP 测试保持全绿
  （现共 94 个）。

### 4.2 前端（Vitest + Testing Library，假时间）

`frontend/src/autosave.test.tsx` 用 mock fetch 与假时钟，逐字验证：

1. 新建后继续敲字，停顿后**一定**再发 PUT、修订号前移（回归 1.2）；
2. 没有净改动不发 PUT，不白产生新修订；
3. 在途保存未返回时继续敲字：不并发第二个 PUT，返回后以**新修订号**
   把含新旧内容的全文再存一次，且不重发已存内容；
4. 另一个标签页先存 → 409 弹冲突框，写明双方修订号、编辑器锁定、
   本地内容不丢；
5. 采用服务器版本 / 保留我的（以 current_revision 另存）/ 手动合并
   （合并文本以 current_revision 保存）三条路径的请求序列与最终状态。

前端测试同样可做红绿对照：旧的自动保存实现无法通过用例 1/3/4。

### 4.3 未改变的既有行为

解析、切页、围栏与容错、增量预览与全量逐字段一致、按修订号取回
历史版本等行为均未改动，相关既有测试全部保持通过。
